Agentic Workflow Engineering Practice

A deeper course for turning agent work from "better prompting" into an engineered system of blocks, gates, tools, reviews, traces, and improvement loops.

Where It Fits

This course is best taken after the core roadmap covers controlled workflow agents and agent runtime design. It expands Stage 3 and Stage 7 into a full engineering practice: design the workflow, encode it in a harness, verify the result, review it, then improve the system from real evidence.

Outcome

Design workflows as systems

Decompose agent work into blocks with explicit inputs, outputs, transitions, stop conditions, and quality gates.

Outcome

Codify reusable practice

Turn prompts, skills, templates, hooks, commands, and subagents into repeatable engineering assets.

Outcome

Verify beyond vibes

Use deterministic checks first, semantic review where needed, and evals to detect workflow regressions.

Outcome

Operate the loop

Use WAL notes, retrospectives, metrics, and research spikes to improve the workflow without overfitting it.

Modules

Module 1

Concept Of Agentic Workflow

Treat a workflow as a graph of blocks, not a pile of prompts. Learn where deterministic code, model calls, validators, and human checkpoints belong.

Practice: map one real task into states, transitions, gates, and failure points.

Module 2

Tools Inside The Harness

Design skills, commands, hooks, subagents, and team patterns as codified process. Keep orchestration predictable as capability grows.

Practice: build one reusable skill or command for a recurring engineering task.

Module 3

Tools Outside The Harness

Use one-shots, JSON contracts, code generation, MCP, CLI tools, and project context without letting tool failures poison the workflow.

Practice: produce a scriptable block that fails closed on malformed output.

Module 4

Implementation Phase

Compare direct implementation, goal-driven loops, verification loops, and team-style execution. Use templates to carry standards into repeated work.

Practice: run the same change through two strategies and compare quality, latency, and review cost.

Module 5

Planning On Steroids

Turn vague tasks into executable plans with Definition of Done, missing-requirement discovery, consensus checkpoints, and bounded research spikes.

Practice: write a plan that another agent could execute without guessing the intent.

Module 6

Review And Everything After

Review AI-assisted changes by intent, invariants, edge cases, and operational behavior. Detect endless fix loops before they waste the day.

Practice: create a self-review and post-merge observation checklist for one change.

Module 7

Continuous Improvement Loop

Use write-ahead logs, evals, and retrospectives to improve the workflow itself. Decide when to tune a block and when to redesign the graph.

Practice: convert a logged failure into a measured improvement proposal.

Module 8

Next Operating Layer

Budget token cost, share workflows with a team, draw boundaries around AI documentation, and keep human judgment in the places it belongs.

Practice: write a rollout memo for a workflow other engineers can adopt.

Practice Studios

Studio 1

Studio 2

Harness Tools

Studio 3

Implementation Strategies

Solve one task directly, then through a verification loop, and compare the diff, tests, and review burden.

Studio 4

Planning Pipeline

Diagnose a raw task, define done, run a bounded research spike, and finish with an executable plan.

Studio 5

Review System

Run self-review, automated quality checks, doom-loop diagnosis, and post-merge observation planning.

Studio 6

Improvement Loop

Keep a WAL, build a tiny eval set, run a retrospective, and choose one workflow change to measure.

Studio 7

Full Cycle

Take one task from intake to plan, implementation, verification, review, observation, and workflow improvement.

Completion Gate

  • Workflow graph has named states and transitions.
  • Every block has an input, output, owner, and failure mode.
  • Quality gates include deterministic checks where possible.
  • Risky actions require approval or dry-run behavior.
  • Structured outputs are validated before reuse.
  • Runs have traces, WAL notes, and replayable examples.
  • Review checks target intent, invariants, and edge cases.
  • One retrospective led to a measured workflow change.
