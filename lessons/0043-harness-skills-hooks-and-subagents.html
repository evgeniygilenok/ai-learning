The One Idea

A harness asset should encode an engineering process: when to run, what context it needs, what it must produce, and how the result is verified. These are real, documented mechanisms, not metaphors: see the Claude Code docs for skills, hooks, and subagents. Cursor has equivalents, and this workspace's own .codex/skills/teach/SKILL.md is a working example.

The goal is not more automation. The goal is to make the right behavior cheaper to repeat than the wrong behavior.

Skill

Use for a repeatable process with prerequisites, steps, output format, and a definition of complete.

Command

Use for an explicit user-invoked workflow, especially when the task has a stable input and output shape.

Hook

Use for a narrow behavior change at a known event, such as before edits, after tests, or before handoff.

Subagent

Use when a bounded specialist can work with scoped context and return a compact artifact to the orchestrator.

type HarnessSkill = {

Context Discipline

Do not hand every helper the whole project. Give each asset only the context needed for its job, then require a result that the next block can validate.

This is how subagents stay useful instead of becoming parallel confusion machines. Anthropic frames the same idea as an attention budget: find the smallest set of high-signal tokens that maximizes the outcome (Effective context engineering).

Interactive Drill: Pick The Harness Asset

You repeatedly need the agent to produce a PR review packet with risk, tests, and rollout notes.

Before any file edit, you want the agent to state which files it will touch and why.

A specialist should inspect only eval traces and return failure clusters to the main agent.

Try It Cold

Draft the frontmatter and section headers of a SKILL.md for this repeated task: "generate a retrieval eval report from the latest eval run." Write yours before revealing the model answer.

Reveal a model answer 
---
name: retrieval-eval-report
description: Generate a retrieval eval report from the
  latest eval run results. Use when the user asks for
  an eval report or after an eval run completes.
---

## Prerequisites
- evals/results/*.json exists for the target run
- golden question set version is recorded in the run

## Steps
1. Load the latest run and the previous baseline run.
2. Compute hit rate, citation correctness, answerability.
3. Diff against baseline; list regressions with case ids.
4. Write docs/retrieval-eval-report.md using the template.

## Output
docs/retrieval-eval-report.md with metrics table,
regression list, and one recommended next action.

## Verification
Report must cite real case ids; regression count must
match the diff; fail if baseline run is missing.

Compare: did yours state when the skill triggers, what already has to exist, and a verification step that can fail? Those three are what separate a skill from a saved prompt.

Design Smell

If a hook or skill works only because you remember hidden local assumptions, it is not reusable yet. Write the assumptions into prerequisites or remove the dependency.

Build Assignment

Build a real skill in your actual harness, not on paper. Create a skill file (for example .cursor/skills/<name>/SKILL.md, .claude/skills/<name>/SKILL.md, or .codex/skills/<name>/SKILL.md) for one repeated task in your portfolio workflow:

  • Name the repeated task it standardizes.
  • List prerequisites and required context.
  • Define the output artifact and schema.
  • Add a verification step that can fail.
  • Write one example input and one expected output.

Then invoke it once for real. Record what happened, including anything the skill assumed that it should have stated, in docs/agentic-workflow-course-notes.md.

Ask the agent to identify which parts are process, which are policy, and which are accidental local setup.
