Lesson 0042 - 35 minutes

A workflow block does one job and proves it is done.

The first move in agentic workflow design is to split the work into blocks with explicit inputs, outputs, gates, and stop conditions.

The One Idea

An agentic workflow is not a long prompt. It is a system of blocks. Some blocks call a model, some run deterministic code, some validate, and some ask a human to decide. Anthropic's Building effective agents describes exactly this shape: chained steps with programmatic "gate" checks between them, and a strong preference for the simplest composition that works.

If a block cannot say what it accepts, what it returns, and how it is checked, it is still a vague instruction rather than an engineering unit.

Block

A bounded step with one responsibility, such as classify ticket, draft plan, run tests, or summarize trace failure.

Transition

The rule that decides the next state from the block output: continue, retry, ask, block, or escalate.

Quality Gate

A check that decides whether the block result is acceptable. Prefer deterministic checks before judgment calls.

Human Checkpoint

A deliberate pause where human judgment is cheaper or safer than letting the workflow guess.

Block Contract

type WorkflowBlock = {
  name: string;
  owner: "app" | "agent" | "human" | "script";
  input: string;
  output: string;
  gate: string;
  onPass: string;
  onFail: string;
  maxRetries: number;
};

Design Rule

Design the workflow so a failure points to a specific block. "The agent did something weird" is not debuggable. "The plan block passed without acceptance criteria" is debuggable.

This is the same instinct as good backend design: isolate responsibility, validate boundaries, and make failures inspectable. It also mirrors OpenAI's agent guidance: orchestration, gates, and approvals live in application code, not inside the prompt.

Interactive Drill: What Is Missing?

"Ask the agent to write a plan, then continue if it looks good."

"Run tests and collect output, but no rule says what happens on failure."

"The agent can merge a security-sensitive auth change after tests pass."

Try It Cold

Write a block contract (name, owner, input, output, gate, onPass, onFail, maxRetries) for this block: "summarize a failing CI run for the on-call engineer." Write yours before revealing the model answer.

Reveal a model answer 
{
  name: "summarize-ci-failure",
  owner: "agent",
  input: "CI run id + raw job logs (truncated to failing steps)",
  output: "JSON: { failedStep, likelyCause, evidenceLines[], suggestedAction }",
  gate: "schema valid AND evidenceLines quote real log lines AND likelyCause != ''",
  onPass: "post-to-oncall-channel",
  onFail: "retry once with full logs; then escalate raw logs to human",
  maxRetries: 1
}

Compare: did your gate check evidence against the input, or only check that output exists? Did your onFail path preserve the raw logs for the human?

Portfolio Habit

For the controlled workflow agent in your portfolio, draw the workflow before writing code. Name each state, block, transition, quality gate, and human checkpoint.

Build Assignment

Create docs/workflow-graph.md in your portfolio repo. Pick one recurring task, such as "turn a vague ticket into a PR-ready plan," and write five block contracts into it:

  • Intake and classify the task.
  • Detect missing requirements.
  • Draft a plan.
  • Run a quality gate on the plan.
  • Ask for approval or return to clarification.

End the file with the workflow graph itself: named states, transitions (including every on-fail path), and where the human checkpoints sit. This file is course job proof; later lessons extend it.

Then ask the agent to challenge whether every block has exactly one job and a checkable output, and to find any transition you forgot.
