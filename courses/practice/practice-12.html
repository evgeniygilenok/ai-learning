What you will demonstrate

  • Convert an ambiguous request into observable acceptance
  • Give a coding agent only the context required for one task

The task contract has observable required behavior, constraints, a limited context packet, and a reviewable result.

Understand the mechanism

'Make escalation clearer' hides several choices. It could mean clearer evidence, a better reason, a more visible pending state, or an honest completion message. Pick one behavior and define a reviewer observation that determines whether it exists.

Keep required behavior separate from optional polish. A task brief should name the file boundary, the acceptance example, the constraints, and the evidence to return. The coding agent can propose a different implementation, but the product promise remains the review target.

Trace the diagram against the worked example. Explain who owns each decision and what evidence reaches the next step.

Worked example

Required: show the exact pending reason, transfer ID, and source IDs before approve. Constraints: no new provider call, no default approval, and no change to saved scopes. Acceptance: running show on an awaiting-approval case displays those fields and no executed-effect claim. Optional polish: shorter labels. Give the agent the brief, CLI projection, job type, and approval contract.

Task: expose pending proposal evidence
Observe: show CASE displays transfer, reason, source IDs, and pending state
Constraints: no implicit approval; preserve stored context
Review: ordinary, missing-evidence, and rejected cases
Return: small diff, observed result, remaining limitation

Run shell examples at the repository root. Commented sketches describe learner code to write; they are not additional installed commands.

Guided build · 30 minutes

  1. Select one unclear behavior found in the product brief or previous run.
  2. Write acceptance examples before implementation. Identify the minimum files and rules the coding agent needs.
  3. Run the task and review the behavior using those examples. Reject extra changes that do not help the chosen task.

Your task · 15 minutes

Turn 'make recovery better' into a second bounded brief. Give another reader enough information to judge completion without your chat history.

Failure investigation · 10 minutes

The implementation hides the pending reason to simplify the output. Check the acceptance example and restore the evidence the operator needs.

Before running, predict the state, evidence, and effect count. Then compare your prediction with the record and name the responsible layer.

Exit explanation · 20 minutes

Could a reviewer determine completion without guessing your intent? What is explicitly optional?

Explain the result in your own words and link the supporting command, code change, or redacted record. A missing prerequisite uses the next session's time.
