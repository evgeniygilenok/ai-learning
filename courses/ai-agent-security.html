AI Agent Security Engineering

Threat-model and harden an action-taking agent across goal integrity, identity, tools, MCP, execution, memory, multi-agent trust, evaluation, and incident response—without turning the lab into a real attack surface.

8 lessons28–38 hours8 reviewable artifacts1 synthetic capstone

Who this is for

  • AI, backend, platform, and application-security engineers building tool-using agents.
  • Experienced TypeScript/product engineers who know HTTP, schemas, authorization, async workflows, tests, and traces.
  • Defenders and technical leads who need reviewable release and incident evidence, not a list of prompt tricks.

What this path is—and is not

You will defend a synthetic procurement/support agent whose model can plan and propose actions while deterministic code retains authority.

This is application/runtime security, not model-weight research, exploit development, compliance certification, or permission to test third parties. It teaches safe reproduction of failure paths against local fake systems.

Prerequisites

Complete Lesson 0014: AI Security Threat Model and the Agent Runtime sequence, Lessons 0031 through 0035, before starting. You should already be able to validate model output, trace a run, make tools idempotent, persist/resume state, enforce approval, and bound tool execution. Review multi-tenant architecture and eval release gates if needed. No offensive-security background is required.

Operating rhythm

ModelUpdate the architecture and threat path before implementing a control.
PreventPlace deterministic enforcement at identity, data, tool, approval, execution, memory, and delegation boundaries.
TestPair every adversarial case with benign utility; score privileged effects from simulator state.
ObserveEmit redacted structured events and exercise independent containment.
DecideMake the release/residual-risk decision from pinned evidence, with owner and revisit trigger.

Common failure patterns

  • A stronger system prompt standing in for authorization.
  • A judge scoring the agent's words while a fake tool shows an unsafe effect.
  • Tenant filtering after retrieval, once forbidden content is already in context.
  • Approval for a vague plan rather than the exact final action.
  • A “sandbox” with host mounts, inherited credentials, or unrestricted egress.
  • Memory treated as trusted chat history with no governed write path.
  • Green stochastic runs with failed trials discarded or versions unpinned.
  • An incident runbook whose kill/revoke permissions have never been tested.

Course safety contract

  • Test only systems you own or have explicit written authorization to assess.
  • Use disposable local targets, fake tools, synthetic tenants/data, and inert canaries.
  • No public scanning, real users, customer data, credentials, money, mail, refunds, or tickets.
  • Deny network by default and tightly cap requests, cost, time, steps, retries, and fan-out.
  • Never execute adversarial text; keep it inert and score simulator state.
  • Stop on scope drift, unexpected effects, real secrets, or another tenant's data.
  • Preserve minimal redacted evidence, revoke exposure, notify the owner, and disclose responsibly.
  • Do not publish secrets, transferable exploit chains, or unredacted sensitive traces.

Capstone and completion gate

Deliver a secure synthetic procurement/support agent: it reads local tickets and approved policy/catalog data, drafts a reply and recommendation, and prepares fake purchase/refund/send/close actions behind deterministic authorization, exact approval, and idempotent effect handling.

  • All eight artifacts match the pinned capstone build.
  • Every threat has invariant, prevention, detection, response, test, and owner.
  • All critical deterministic security cases pass.
  • No observed critical unsafe effect, canary leak, or authorization-isolation violation; denominator and uncertainty reported.
  • Benign utility ≥90% and no more than a five-point drop from accepted baseline.
  • False blocks ≤5%; unnecessary approvals ≤0.25 per successful benign task.
  • Model, prompt, policy, component, dataset, scorer, and sandbox pins recorded.
  • Tabletop demonstrates kill, revoke, quarantine, effect reconciliation, rollback, verified recovery, and owned follow-ups.
  • Assurance case names counterevidence and expiring residual risks.
  • Five-minute demo shows benign success, blocked attack, containment, and recovery.

These are course thresholds for a synthetic system, not a universal production standard. Higher-impact use needs impact-specific limits, independent review, organizational authorization, and applicable legal/privacy assessment.
