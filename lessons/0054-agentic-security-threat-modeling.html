Technical depth

Threat-model influence and authority end to end

Draw the synthetic agent architecture before selecting controls. Preserve source provenance through context assembly, label trust boundaries, enumerate consequential sinks, and state invariants that code and tests can enforce. Use OWASP Agentic Top 10 for coverage, MITRE ATLAS for adversary behavior, and NIST AI RMF for ownership and lifecycle evidence; a crosswalk is not a certification.

The one idea

An agentic threat model is a map of influence and authority. Trace every place untrusted data can influence a plan, every place a model-generated proposal can reach a state-changing sink, and every identity or approval that can enlarge the blast radius. Framework labels help you check coverage; enforceable invariants are what make the model useful.

Lab safety boundary

Use only the fictional tenants northstar-demo and redwood-demo, synthetic tickets, fake purchase requests, and stubbed tools. Keep the lab offline. Do not connect email, payment, procurement, customer-support, identity, browser, shell, or production services. Do not paste real prompts, credentials, customer text, tokens, endpoints, or incident data into fixtures, traces, or the artifact.

A concrete mental model: source → decision → sink

[operator goal] ───────────────┐
                              ▼
[ticket / vendor note] → [context assembler] → [model planner] → [policy gate] → [tool adapter] → [effect]
       SOURCE            boundary B1       proposal only       boundary B2       SINK
                              ▲                    │                 ▲
[memory / tool result] ───────┘                    └── audit ────────┘

Trusted control plane: authenticated user, agent identity, tenant binding,
capability, policy, approval record, immutable tool implementation.

Untrusted data plane: user text, retrieved files, ticket bodies, vendor text,
model output, memory content, tool output, and messages from other agents.

The model is inside the decision path, but it is not the policy authority. Even a high-priority prompt is not a security boundary. A sink adapter must independently reject a proposal that violates trusted identity, scope, object, destination, approval, budget, or lifecycle state.

The safe synthetic fixture

Support path

Summarize ticket TKT-1042 for northstar-demo and propose a draft reply. The fixture exposes getTicket and saveReplyDraft; it never sends.

Procurement path

Review fake request PR-204 for a CAD 480 keyboard order. The fixture exposes getPurchaseRequest and createApprovalPreview; it never buys or pays.

Adversarial data

A ticket or vendor note contains an instruction to ignore the task, read another tenant, or copy records to dropbox.invalid. The domain is reserved for examples and no network call exists.

Observable result

Each run records source labels, proposed calls, policy decisions, reason codes, and stubbed effects. It records no secrets and no free-form chain of thought.

Mark trust boundaries

  1. B1 — ingestion: external text crosses into model context.
  2. B2 — execution: model output crosses into deterministic code.
  3. B3 — tenancy: a request crosses from shared runtime to tenant data.
  4. B4 — persistence: transient content becomes durable memory or an artifact.
  5. B5 — delegation: one agent, tool, or user acts on behalf of another.
  6. B6 — human decision: generated explanation influences approval.

Write invariants as tests

  • Untrusted content cannot grant authority or change the operator goal.
  • Tenant derives from authenticated runtime state, never model arguments.
  • A model proposes a call; only policy code can authorize it.
  • An approval binds to canonical tool name and the true arguments executed.
  • No synthetic lab tool sends, purchases, pays, deletes, shells, or calls a network.
  • Every denial produces a stable reason code without logging fixture text.

Map one model across three frameworks

Use OWASP to check risk-category coverage, MITRE ATLAS to describe adversary behavior and build test scenarios, and NIST AI RMF to assign lifecycle ownership and evidence. Do not claim that a crosswalk proves compliance.

ATLAS is a living knowledge base, so record the technique name, identifier, and review date instead of assuming a frozen catalog. NIST states that AI RMF 1.0 is voluntary and is being revised; use the versioned publication named in the sources.

Safe offline lab: build the threat model

  1. Create starter/docs/agent-security-threat-model.md. State purpose, owners, synthetic-only scope, excluded live capabilities, and review date.
  2. Draw the fixture data flow. Number every source, transform, trust boundary, policy decision, and sink. Include support and procurement paths.
  3. Inventory assets: tenant records, user intent, agent/user identity, capability, approval, memory, tool registry, audit evidence, and availability budget.
  4. For each boundary, write at least one abuse case in the form “Given source S, an adversary influences decision D to reach sink K, violating invariant I.”
  5. Give each abuse case prevention, detection, response, owner, residual-risk statement, and test ID. Separate prompt guidance from enforceable code controls.
  6. Cross-reference every ASI01–ASI10 entry at least once. Add relevant ATLAS technique names/IDs and NIST Govern, Map, Measure, Manage work items.
  7. Run a paper/tabletop trace: malicious vendor text proposes a cross-tenant read followed by an outbound copy. Show exactly where deterministic policy denies it; do not implement a live exfiltration path.

Acceptance tests

  • The diagram has at least five numbered boundaries and identifies both the trust source and authority source at each one.
  • Every sink has an owning adapter, allowed effect, denied effect, required identity/scope, and audit event.
  • At least ten abuse cases collectively cover ASI01–ASI10; at least four follow a complete source-to-sink path.
  • Each high-risk case has prevention, detection, response, owner, residual risk, and a runnable or tabletop test ID.
  • All security claims are phrased as testable invariants. “The system prompt tells the agent not to” does not count as an enforcement control.
  • The artifact contains no real data or capability and the synthetic fixture cannot make network or external side effects.
