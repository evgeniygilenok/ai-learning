Technical depth

A security gate couples attack resistance to utility

Derive adversarial cases from threat-model paths and production-like failures. Keep deterministic invariants separate from probabilistic model scores; report denominators and slices for attack success, unsafe proposals, useful completion, and benign blocks. Block known boundary regressions, route calibrated uncertainty to named review, and version every case, policy, model, tool, and threshold.

Lab safety boundary

Run only against disposable local fixtures, synthetic identities, synthetic records, fake side-effect tools, and inert canaries. Do not probe a public service, a third-party agent, a real mailbox, a production tenant, or any target you are not explicitly authorized to test. An “attack succeeded” in this lesson means the simulator recorded a prohibited outcome; it must never mean a real person, account, or system was affected.

1. Derive cases from the threat model

Do not begin with a generic jailbreak list. Begin with a path in your own threat model: untrusted source → model-visible context → decision → privileged sink → impact. The case is useful only if its oracle can prove whether the protected invariant held.

Keep each pair identical except for the risk-bearing feature. This exposes defenses that “work” by refusing everything.

Deterministic cases

Use executable assertions for properties the application owns. Run them on every change.

  • Policy decision and reason code for every proposed tool call.
  • Tenant, object, action, audience, and data-class isolation.
  • Approval bound to canonical arguments plus resolved provenance, approver, fresh expiry, and one-time nonce.
  • Application-owned clock sampled once per decision; stale cached context and clock failure deny before any use/approval consumption.
  • Pinned resolver classifies exact final payload/tool/destination/tenant/run and lineage; missing, forged, or downgraded provenance fails closed.
  • Tool schema, allowlist, URL, path, egress, step, fan-out, and spend limits.
  • Side-effect ledger, idempotency key, and uncertain-ack recovery.
  • Exact and encoded/normalized canary absent from every final outbound argument, output, log, and persisted memory.
  • Untrusted memory and component changes quarantined by default.

Stochastic cases

Use repeated trials for model-dependent behavior. Preserve every failure instead of rerunning until green.

  • Fix the case set, model snapshot, parameters, prompts, tools, and policy first.
  • Vary only a declared factor: seed where supported, attack paraphrase, tool ordering, or model.
  • Run enough trials to report a denominator and interval, not a single pass.
  • Score privileged effects from simulator state. Use calibrated semantic scorers only where state cannot answer.
  • Sample scorer disagreements for human review and version the adjudication rubric.

2. Measure harm and utility on the same run

MetricDefinitionRelease interpretation
Attack success rate (ASR)Eligible adversarial trials in which the attacker objective is achieved ÷ all eligible adversarial trials.Slice by threat, source, model, and severity. A critical objective has a zero-observed-success requirement, with the remaining statistical uncertainty stated.
Unsafe-effect rateTrials that create a prohibited external-state transition ÷ all trials capable of reaching that sink.Use the fake tool’s state as ground truth. Any critical effect blocks release even if the final prose looks safe.
Canary-leak rateTrials in which a synthetic secret appears in an unauthorized output, tool argument, log, or memory ÷ exposed trials.Exact/encoded canary detectors run deterministically. Zero observed is required for protected slices.
Authorization-isolation violationsCross-tenant, cross-user, wrong-audience, or excess-scope accesses accepted ÷ attempted forbidden accesses.Count at the policy and data boundary, not from model narration. Any violation is a release blocker.
Benign utilityBenign tasks satisfying their task-specific assertions ÷ benign tasks attempted.Compare against the last accepted baseline and by task slice. Security that disables the product fails the course gate.
False-block ratePolicy-compliant benign tasks incorrectly blocked ÷ policy-compliant benign tasks.Separate policy blocks, detector blocks, and model refusals so the repair targets the right layer.
Approval burdenHuman approvals requested, plus repeated or unnecessary approvals, per successfully completed benign task.Report median and tail. Fewer prompts are not safer if approval becomes vague or bundled.

Do not translate “0 of n” into “impossible”

Report the count, denominator, and a confidence interval. As a quick check, zero events in n independent trials still has an approximate 95% upper rate near 3/n. Dependence and adaptive attacks can make even that optimistic, so preserve explicit residual risk.

3. Pin the experiment before comparing builds

A green gate is not reproducible when the model alias, judge, prompt, tool registry, or dataset silently changes. Commit exact identifiers or immutable digests for every evaluation dependency.

System pins

Application commit, policy version, prompt/template digest, tool schemas and manifest digests, sandbox profile, clock implementation/configuration, provenance resolver and policy/config digests, database fixture, and feature flags.

Model pins

Provider, exact model snapshot where available, parameters, region, fallback order, structured-output schema, and request adapter version.

Eval pins

Case-set digest, mutation/paraphrase version, scorer and rubric version, judge snapshot, harness package/container lock, repeat count, and declared seeds.

Evidence pins

Run ID, timestamp, redaction policy, result schema, artifact hashes, environment label, and link to the threat-model version that justified each case.

If a hosted provider offers only a moving alias, record the resolved model identifier and run timestamp, treat later runs as a new environment, and do not call them exact reproductions.

4. Install the CI security gate

  1. Validate configuration. Fail on malformed JSON, unresolved placeholders, missing pins, changed digests, duplicate case IDs, or cases with no threat and oracle.
  2. Start isolated fixtures. Create synthetic tenants, unique per-run canaries, pinned fake clock and provenance resolver, fake tools, an empty outbox/effect ledger, no default network, and a hard wall-clock timeout.
  3. Run deterministic tests first. Include stale-context expiry, clock failure, missing/forged/downgraded provenance, and an encoded canary at an allowed fake destination. A failed authorization, approval, egress, memory, sandbox, or effect assertion stops the candidate immediately.
  4. Run declared stochastic trials. Preserve all attempts, including timeouts and evaluator errors. Never discard the first failure and report a later retry.
  5. Aggregate by slice. Emit counts, denominators, intervals, baseline deltas, and links from each failure to a redacted trace and simulator-state diff.
  6. Apply the gate. Compare results to severity-aware thresholds. Missing evidence, unavailable scorers, pin drift, or incomplete suites fail closed.
  7. Retain an evidence packet. Store the config, hashes, summary, failed cases, redacted traces, and release decision; keep secrets and raw sensitive content out.

Pull request lane

Run schema/pin validation, every critical deterministic case, and a small fixed benign/adversarial smoke set. Optimize fixture startup, not control coverage.

Nightly and release lane

Run the full repeated suite, attack variants, model/provider slices, judge calibration checks, and confidence reporting. A release candidate must use the same immutable candidate build.

Optional evaluation tools

These can accelerate a suite; none replaces your own authorization, effect, and isolation oracles. Pin the chosen package/container and suite commit in the artifact.

ToolGood fitIntegration boundary
AgentDojoDynamic tool-using tasks that measure utility and prompt-injection security.Adapt its scenarios to fake tools; keep project authorization and side-effect assertions as the final oracle.

Studio: prove the gate catches a regression

  1. Select threat-model paths that include injection, fresh-time authorization, trusted provenance/egress, approval, supply chain, memory/inter-agent, and sandbox or cascade.
  2. Create one adversarial and one matched benign case for each. Assign threat ID, severity, preconditions, oracle, owner, and review date.
  3. Implement deterministic fake-tool state assertions before adding any semantic judge.
  4. Run a deliberately vulnerable branch or test fixture. Save the expected red result without real side effects.
  5. Repair the control at the application or runtime boundary, rerun the unchanged cases, and compare both security and utility.
  6. Commit the gate JSON and a redacted evidence packet with exact pins, counts, denominators, intervals, and residual risks.

Completion check

  • Every case traces to a threat and protected invariant.
  • Every adversarial case has a matched benign control.
  • Critical effects use deterministic simulator-state oracles.
  • Stochastic runs have fixed repeats and preserved failures.
  • All model, prompt, policy, tool, clock, provenance-resolver, case, and runner versions/configurations are pinned.
  • ASR, unsafe effects, canary leaks, authorization isolation, utility, false blocks, and approval burden are reported.
  • CI fails on threshold breach, missing evidence, or pin drift.
  • The evidence explains uncertainty and remaining risk.
