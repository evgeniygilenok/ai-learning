Understand the mechanism

The model receives a request assembled by your application. It can propose a tool call or produce text. A plausible sentence does not establish a transfer's status. Only a permitted lookup supplies that fact. Start by tracing the boundary between what you sent, what came back, and what application code accepted.

The fake provider is a fixture. Its scripted lookup proves that the runtime can handle a particular proposal. It supplies no evidence about a real model's judgment. Keep fake and real records distinct, including the model returned by the provider rather than only the model you requested.

Trace the diagram against the worked example. Explain who owns each decision and what evidence reaches the next step.

Worked example

The baseline case asks why tr_001 is pending. The application supplies a two-business-day policy. lookupTransfer returns three business days pending. A useful escalation reason cites those two facts. If the model instead says the transfer has settled, first inspect the tool output and final text. The model invented a status; a successful HTTP request did not make its answer correct.

Guided build · 30 minutes

  1. Run the fake baseline and mark the user text, retrieved policy, proposed lookup, tool result, and pending write.
  2. Open provider.ts and follow ModelRequest through the Responses adapter. Locate response ID, actual model identity, usage, timeout, and tool arguments.
  3. Use the operating guide to configure a bounded real run under a new event ID. Record output validity, latency, token use, estimated cost, and one limitation. Redact content before saving evidence.

Your task · 15 minutes

Investigate a second question about the same synthetic transfer. Write a request-and-result record without using the model's explanation as proof of correctness. Compare its actual behavior with the fake fixture.

Failure investigation · 10 minutes

Use a scripted provider response that returns text before the required lookup. Predict the runtime's premature-termination outcome, then inspect it. Preserve the injected failure and later add one genuine model failure to the same record.

Before running, predict the state, evidence, and effect count. Then compare your prediction with the record and name the responsible layer.

Exit explanation · 20 minutes

Which fact came from the model, which came from a tool, and which came from policy? Explain why output validity and factual correctness need separate checks.

Explain the result in your own words and link the supporting command, code change, or redacted record. A missing prerequisite uses the next session's time.
