Understand the mechanism

A project knowledge index is a short map to authoritative documents. It should answer where to find the approval rule, the current architecture, and the operating commands. It need not repeat those documents or preserve the entire conversation.

Give each rule an owner and source. A dated decision can explain why the project uses a terminal interface. Temporary research should carry an expiry or revisit condition. When rules conflict, stop the affected change and resolve the source conflict before encoding either rule in code.

Trace the diagram against the worked example. Explain who owns each decision and what evidence reaches the next step.

Worked example

An index points to product-brief.md for the operator's task, architecture.md for runtime boundaries, and agentic-engineering-practice.md for local commands. A task brief links the approval rule and asks for a clearer pending-proposal label. The coding agent needs those sources and the CLI file. It does not need every lesson or your previous chat.

# Learner knowledge index
- Product promise: product brief, named owner and review date
- Runtime boundary: architecture and approval contract
- Current task: bounded brief with observable acceptance
- Temporary research: source, date, and revisit trigger

Run shell examples at the repository root. Commented sketches describe learner code to write; they are not additional installed commands.

Guided build · 30 minutes

  1. Create a learner-owned index using existing product and architecture documents. Mark which rules apply to the coding agent and which apply to the runtime product.
  2. Write one small task that names its necessary sources and expected artifact.
  3. Start a fresh coding-agent session with the index and task. Record which sources it actually found and repair a broken or ambiguous pointer.

Your task · 15 minutes

Introduce a stale note that conflicts with the current approval rule. Ask a fresh session to identify the conflict and propose its resolution. Keep the final source decision in your own record.

Failure investigation · 10 minutes

An agent reads an old note that says escalation is automatic. Inspect the resulting proposal. Check that the runtime still pauses even if the coding-agent instructions were poor.

Before running, predict the state, evidence, and effect count. Then compare your prediction with the record and name the responsible layer.

Exit explanation · 20 minutes

Where does a fresh session find the current rule, and who decides whether a temporary finding becomes a durable rule?

Explain the result in your own words and link the supporting command, code change, or redacted record. A missing prerequisite uses the next session's time.
