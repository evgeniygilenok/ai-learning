Lesson 0047 - 40 minutes

Review AI-assisted code against intent, not just syntax.

A useful review system starts before the PR, checks the diff against the plan, and feeds repeated failures back into the workflow.

The One Idea

AI code review is not "let another model comment on the diff." It is a layered process: self-review, deterministic checks, semantic review, human judgment, and post-merge observation.

The review target is the contract: what the change was supposed to do, what it must not break, and what evidence proves it. The baseline checklist is the classic one — design, functionality, complexity, tests, naming, documentation (Google's What to look for in a code review) — with AI-specific layers on top: intent drift, hidden assumptions, and generated complexity nobody asked for.

Self-Review

The implementer checks intent, edge cases, assumptions, tests, and unnecessary generated complexity before team review.

Automated First Pass

Lint, types, tests, security checks, eval smoke tests, and trace assertions remove obvious failures.

Human Review

The reviewer spends attention on judgment: tradeoffs, invariants, product behavior, and operational risk.

Post-Merge

Logs, traces, metrics, and user feedback reveal what review could not prove ahead of time.

Doom-Loop Signal

If every AI-suggested fix creates a new unrelated issue, stop the loop. Return to the last good checkpoint, narrow the task, or rewrite the plan.

More iterations are not automatically more quality. Sometimes they are just drift. Google's review standard has the same spirit for humans: seek continuous code-health improvement, not perfection through endless rounds (The standard of code review).

Try It Cold

An agent implemented "add retry to the embedding call." The diff touches the retry helper, the embedding client, and, unexpectedly, the ingestion queue config. Write the three reviewer questions you would ask first, then reveal.

Reveal a model answer
  • Why did the queue config change? The plan scoped retries to the embedding call; an unexplained third surface is either hidden coupling or scope creep, and it decides whether this is one change or two.
  • What happens on retry exhaustion? Intent was resilience; the failure path (dead-letter, alert, drop?) is where the real behavior contract lives, and where an agent most likely guessed.
  • Are the retries idempotent and budgeted? Re-embedding the same chunk is wasteful but safe; re-enqueueing ingestion work may not be. This is the invariant the diff must prove, not assert.

Compare: did your questions target intent, invariants, and the unexplained surface, or line-level style? The first three findings in AI review are almost always assumption-shaped.

Reviewer Habit

Ask where the agent guessed. The most important review comments often point to hidden assumptions, not broken syntax.

Build Assignment

Create docs/workflow-review-checklist.md in your portfolio repo with sections for:

  • Intent and Definition of Done.
  • Changed files and ownership boundaries.
  • Tests, evals, and trace evidence.
  • Edge cases and rollback plan.
  • Slopwatch: generic comments, over-abstraction, unused flexibility.
  • Post-merge signals to watch.

Then run it for real: ask the agent to apply the checklist to one actual past diff from your repo and return only findings that cite a file or requirement. Record the findings, and one checklist improvement they revealed, in docs/agentic-workflow-course-notes.md.
