Technical depth

Context and memory need provenance plus write authority

Authenticate inter-agent envelopes and preserve sender, tenant, purpose, source, timestamp, expiry, and delegation limits. Quarantine untrusted writes, require promotion policy for durable memory, prevent transitive authority, and support revocation and rebuild. Test poisoning, replay, stale context, cross-tenant reads, and summary laundering across multiple hops.

Lab safety boundary

Use two fictional tenants, fake agents, in-memory storage, verified-envelope fixtures, inert instructions, and no network. Do not connect a live vector database, messaging platform, A2A/MCP endpoint, identity provider, or long-term personal memory. Test message authentication with pre-verified fixtures or reviewed libraries—not home-grown production cryptography.

The one idea

Content can be authentic and still be untrusted for authority. A signed peer may send a wrong fact; an approved document may contain an injected instruction; a correct summary may lose the tenant label that made it safe. Treat received trust and data-class labels as claims. Resolve provenance locally in application code, bind the result to the exact content digest and lineage, sample receiver-owned fresh time, and re-authorize every memory read, write, delegation, and sink.

Use a context envelope, not a string pile

type ContextEnvelope = Readonly<{
  contextId: string;
  contentRef: string;       // opaque fixture reference
  sourceKind: "policy" | "user" | "document"
    | "tool" | "memory" | "peer";
  sourceId: string;
  trust: "trusted_control" | "untrusted_data";
  tenantId: string;
  subjectRef: string;
  sessionId: string;
  purpose: string;
	  dataClasses: readonly string[]; // received claims, never authority
	  resolvedClassificationRef: string; // app-issued; binds digest + lineage
  createdAt: string;
  expiresAt: string;
  parentRefs: readonly string[];
  contentDigest: `sha256:${string}`;
	}>;

Assembly invariants

  • Authorization selects sources before content reaches the model; filtering afterward is too late.
  • Policy/control context is stored separately and can be changed only through its trusted control-plane path.
  • Retrieved, tool, memory, and peer content remains untrusted data even if relevant, signed, or previously summarized.
  • Every transform derives a new envelope that retains all parents; missing tenant/trust/purpose fails closed.
  • Received labels are claims. A pinned application resolver reclassifies the exact bytes/artifact and binds its decision to contentDigest, parent lineage, tenant, purpose, and resolver version.
  • Compaction preserves decisions, rejections, approvals, effect IDs, budgets, resolver-issued provenance, and expiry—not just prose.
  • Trace, cache, scorer, and memory access enforce the same tenant/data-class boundary as retrieval.

Memory is a state machine

candidate→validated→active→expired / deleted
any non-final state→quarantined→restored or deleted
  1. Propose: the model may propose a typed candidate; it cannot write directly.
  2. Resolve: a trusted application resolver classifies the exact content digest and lineage; missing, malformed, forged, or downgraded provenance fails closed.
  3. Authorize: deterministic policy samples fresh application time and verifies writer, tenant, subject, purpose, type, source, TTL, resolved data class, and prohibited content class.
  4. Validate: resolve factual sources where possible; distinguish user preference from externally asserted fact; require review for sensitive durable classes.
  5. Activate: version the entry and indexes. Retrieval returns the entry plus its envelope, never naked text.
  6. Use: re-resolve and authorize each read for the exact body/artifact, current tenant, session, purpose, and agent; lower confidence/trust when transformations lose fidelity.
  7. Expire/delete/quarantine: remove from retrieval immediately, keep minimal governed tombstone/evidence, find derived summaries, and rebuild affected indexes.
  8. Rollback: select a known-good version and prove later runs no longer retrieve poisoned or derived content.

A summary can launder trust

If untrusted vendor text becomes “the agent remembers that policy allows this vendor,” the wording changed but provenance did not. Derived memory inherits the most restrictive tenant, trust, data-class, purpose, and expiry of its parents unless a named validation process explicitly upgrades a specific property. A model cannot perform that upgrade on its own.

Authenticate the peer; authorize the delegation

Verified message envelope

Receiver checks

  1. Authenticate transport/server and obtain sender identity outside message content.
  2. Sample receiver-owned time now; validate schema, protocol version, audience, expiry, nonce, body digest, and replay store. Never reuse a context-carried time for authority.
  3. Bind user, tenant, session, parent task, and purpose to trusted state.
  4. Locally resolve classification for the exact body/artifact digest and lineage; sender labels are claims, and missing, forged, or downgraded resolution denies.
  5. Verify requested skill/action/data against local policy and the attenuated capability.
  6. Require child budgets to be no larger than every remaining parent budget.
  7. Treat message body/artifacts as untrusted data; validate outputs before reuse or effect.
  8. Record parent/child edge, decision, reason, and cancellation route without raw sensitive text.

Protocols can advertise authentication requirements, but the receiving application remains responsible for authorization at skill, data, action, and downstream-tool boundaries. Never accept an in-payload “I am the system agent” claim as identity.

Build context-integrity-policy.md

  1. Declare scope, owners, synthetic fixture IDs, policy/protocol versions, source review date, prohibited production use, and links to ASI06–ASI08 threat paths.
  2. Define the context envelope and authority table for control, step, session, durable memory, and peer-exchange zones.
  3. Write assembly rules for authorization-before-retrieval, received-label claims, local provenance resolution bound to exact digest/lineage, compaction, cache/trace/scorer isolation, and missing-resolution failure.
  4. Specify allowed memory types, writer/readers, tenant/subject/purpose scopes, validation, TTL, confidence, prohibited classes, state transitions, quarantine, deletion, derived-data discovery, and rollback.
  5. Specify the verified delegation envelope, transport identity boundary, receiver-owned fresh clock, local authorization, capability attenuation, replay store, message/task lifecycle, cancellation, and budget accounting.
  6. Implement the policy with in-memory stores and a fake message bus that opens no network. Use pre-verified sender fixtures; do not implement custom production signatures.
  7. Run the required paired cases and save decisions, reason codes, versioned state diffs, bounded graph, and clean rollback evidence without raw hostile text.

Acceptance gate

  • Every context item has origin, trust, tenant, subject/session, purpose, claimed class, app-resolved class/reference, digest, lifetime, and lineage.
  • Unauthorized content never enters model context, trace, cache, scorer, or memory.
  • Durable memory has typed writes, explicit readers, validation, TTL, quarantine, delete, derived-data cleanup, and rollback.
  • Credentials, identity/role claims, policy, approvals, and free-form instructions cannot become memory.
  • Peer identity comes from verified transport; body and classification claims never establish identity, authority, or data sensitivity.
  • Delegated capability and all budgets only shrink; audience, tenant, object/data, skill/action, fresh expiry, and purpose are re-authorized locally.
  • Stale time, missing/forged/downgraded provenance, replay, mutation, wrong audience, cross-tenant access, cycles, fan-out, depth, retries, and cancellation are deterministically tested.
  • All tests use in-memory synthetic fixtures and a no-network fake bus.
