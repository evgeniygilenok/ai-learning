The One Idea

An agent workflow that only works for its author is a personal habit, not a team system. Team rollout requires explicit setup, versioning, permissions, cost expectations, and ownership.

The human role does not disappear. It moves toward intent, tradeoffs, accountability, and deciding when the workflow should stop.

Token Economics

Know which blocks spend context and why. Track latency and cost as design signals, not trivia. Anthropic frames context as a finite attention budget to spend deliberately (Effective context engineering).

Team Reproducibility

Document setup, required tools, secrets, versioning, local assumptions, and failure recovery. Harnesses support this natively: skills and hooks are shareable files that can be versioned and bundled for a team (Claude Code skills).

Documentation Boundaries

Separate docs for humans from docs used as agent context. Each has different quality rules.

Human Responsibility

Keep humans accountable for intent, architecture tradeoffs, approvals, and organizational risk.

Document Intake

For weakly structured documents, first decide the retrieval and context strategy. Do not throw a whole messy corpus into the agent and call it memory.

Good document workflows preserve source, structure, permissions, freshness, and answerability.

Interactive Drill: Team-Ready Or Personal Habit?

"Run my local command after setting the same env vars I always use."

"The workflow has setup docs, permissions, sample inputs, expected outputs, and known failure modes."

"The agent can choose whether a risky architecture tradeoff is acceptable for the business."

Try It Cold

Pick the adoption metric for this rollout: a workflow that turns support tickets into triaged, prioritized briefs for the on-call engineer. Name the metric, how it is measured, and one metric you deliberately rejected. Then reveal.

Reveal a model answer

A strong choice: percentage of on-call shifts that use the generated brief without regenerating or discarding it, measured from run logs plus a one-question shift survey. It captures real adoption (people choosing to rely on the output) rather than activity. A tempting metric to reject: number of briefs generated. It goes up even when nobody reads them, and it rewards running the workflow rather than trusting it. Time-saved estimates are also weak at first: they are self-reported and drown in shift-to-shift noise until adoption is stable.

Completion Gate

Before sharing a workflow, make another person run it from the docs. Their friction is part of the system, not a side note.

Build Assignment

Write a one-page rollout memo for your agentic workflow and commit it as docs/workflow-rollout-memo.md:

  • Purpose and non-goals.
  • Who owns the workflow and who can approve risky actions.
  • Setup, secrets, tools, and sample inputs.
  • Cost and latency expectations.
  • Known failure modes and support path.
  • Adoption metric: time saved, review defects caught, eval pass rate, or setup success.

Then run the completion gate for real: ask the agent to act as a new teammate following only the memo, and have it point out every step that assumes hidden knowledge. Fix the top findings, and note them in docs/agentic-workflow-course-notes.md. This memo is the final artifact of the course; also write a learning record (learning-records/) if the course changed how you think about agent work.
