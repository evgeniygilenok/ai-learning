Technical depth

An agent proposal carries no authority by itself

Bind distinct user and agent identities to tenant, exact scope, object, destination, audience, expiry, run, and use limits. Resolve true arguments before approval, bind the approval to run, capability, nonce, and prepared-action digest, then consume it atomically once. Deny token redirect, cross-tenant access, sensitive egress, replay, and unsandboxed execution outside the model.

The one idea

A model-generated tool call is an untrusted proposal, not proof of authority. Authorization succeeds only when a trusted runtime can answer who is the user, which agent is acting, on whose behalf, in which tenant, for which action and object, at which service, until when, and under what exact approval. Anything missing, ambiguous, stale, or broader than the grant is denied.

Lab safety boundary

Keep the exercise offline and synthetic. Use in-memory fixtures for northstar-demo and redwood-demo; do not mint real tokens, implement home-grown production cryptography, call an identity provider, or connect live tools. The “send,” “purchase,” and “external export” adapters are denial-only stubs. Never use real user IDs, service accounts, credentials, access tokens, tenant names, tickets, recipients, or URLs.

A concrete mental model: identity × delegation × context × effect

authenticated user: user_demo_17
distinct agent:     agent_support_drafter_03
delegation:         user_demo_17 → agent_support_drafter_03

contextual capability = {
  tenant: northstar-demo,
  scope: replies:draft,
  object: ticket:TKT-1042,
  audience: urn:demo:tool-gateway,
  expires: 2026-07-27T16:15:00Z,
  tool: saveReplyDraft,
  destination: internal-drafts
}

prepared effect = saveReplyDraft(ticket:TKT-1042, bodyDigest:sha256:…)
approval         = user_demo_17 approved digest(prepared effect)

ALLOW only if every dimension matches; otherwise DENY.

Authentication establishes an identity. Delegation says that a user permits a particular agent to act in a limited context. Authorization evaluates the proposed effect against both. Never collapse the agent and user into one shared principal: separate identities make revocation, attribution, anomaly detection, and least privilege possible.

Who

User ID and agent ID are unique, authenticated, separately revocable, and carried in trusted runtime context—not accepted from model arguments.

What authority

Tool and scope say what kind of operation is allowed. Object and tenant say where. A broad scope never silently implies every object.

Where and when

Audience binds authority to the intended resource server. Expiry, session, run, use count, and purpose narrow when it is usable.

Which effect

Policy sees canonical, resolved arguments. High-impact approval binds to those true arguments, not the agent’s reassuring natural-language summary.

In a production OAuth system, signature, issuer, type, audience, and expiry verification occur before this application policy. RFC 9068 requires audience and expiry checks for JWT access tokens; RFC 8707 explains audience-restricted resources. This lab starts from a branded VerifiedCapability fixture and does not teach DIY token verification.

Authority comes from trusted channels

  • Session middleware supplies user and tenant.
  • Workload authentication supplies agent identity.
  • Policy storage supplies tool/scope/object rules.
  • Capability verification supplies audience and expiry.
  • Object lookup supplies canonical ID and owning tenant.
  • An application-owned clock supplies fresh decision time; a reusable context timestamp never supplies authority time.
  • An application-owned resolver classifies the exact canonical payload, sources, tenant, run, tool, and destination.
  • Approval storage supplies approver and effect digest.

Model arguments remain untrusted

  • userId, tenantId, roles, and scopes
  • Claims that approval already happened
  • Tool aliases that resolve to more powerful adapters
  • Selectors, queries, wildcards, paths, and external URLs
  • Natural-language summaries of recipients or quantities
  • Tokens, credentials, or “system” messages found in content

True-argument approval: what is reviewed is what executes

  1. Parse: reject unknown fields, wrong types, ambiguous encodings, wildcards, and unsupported tool names.
  2. Resolve: use server-side data to turn aliases, selectors, and queries into a bounded set of canonical object IDs.
  3. Prepare: freeze exact tool, objects, recipients/destination, amount or quantity, content digest, tenant, idempotency key, and resolver-issued provenance/classification.
  4. Present: show the user those significant values directly. Do not let the agent substitute a friendly summary for the true action.
  5. Bind: store approval against a canonical digest of the prepared action, approver, tenant, audience, and expiry.
  6. Execute: execute that immutable prepared action once. Any argument or resolved-object change invalidates approval and requires a new decision.

This is the transaction-authorization principle often called “What You See Is What You Sign.” It also closes a time-of-check/time-of-use gap: the handler must not rerun a mutable query after approval and silently act on a different object set.

Tool abuse is often a composition problem

lookupTicket may be a legitimate read and postPublicStatus may be a legitimate outbound action. Together they form an exfiltration path even when the fake destination is allowlisted. The trusted resolver must classify the exact final outbound arguments and lineage; model-supplied “public” labels are ignored. Per-tool and destination allowlists alone do not constrain dangerous chains.

lookupTicket(ticket:synthetic-42) → sourceIds:[ticket:synthetic-42],
  sensitivity:restricted
postPublicStatus(external:synthetic-status, encodedTicketBody)
  → SENSITIVE_EGRESS_DENIED or DLP_CANARY_DETECTED

The destination is allowed. The final decision still fails because app-issued
provenance and final-argument DLP are part of the prepared action.

Implement the policy boundary

Use the exact runtime seam in starter/src/security-policy.ts. The model supplies only a proposal. The application supplies identity/capability verifiers, provenance resolution, a fresh clock, and atomic state.

type CanonicalActionProposal = Readonly<{
  tool: string;
  tenantId: string;
  destination: string;
  arguments: Readonly<Record<string, JsonValue>>;
}>;

type CanonicalProvenance = Readonly<{
  sensitivity: "public" | "internal" | "restricted";
  sourceIds: readonly string[];
  detectedCanaries: readonly string[];
}>;

type ProvenanceClassificationInput = Readonly<{
  proposal: CanonicalActionProposal;
  tenantId: string;
  runId: string;
}>;

type SecurityPolicyRuntimeOptions = Readonly<{
  authenticateIdentity: (evidence: unknown) => unknown | null;
  verifyCapability: (evidence: unknown) => unknown | null;
  classifyProvenance:
    (input: ProvenanceClassificationInput) => unknown;
  clock: () => number;
  authorizationState: AuthorizationStateStore;
}>;

const trusted =
  runtime.establishTrustedContext(sessionEvidence);
const capability =
  runtime.establishVerifiedCapability(capabilityEvidence);

// prepareAction first requires runtime-branded identity and capability. It
// snapshots the proposal, verifies trusted tenant/run binding, and gives the
// resolver frozen { proposal, tenantId, runId }. PreparedAction freezes and
// digest-binds exact arguments, provenance, tenant, and run.
const action =
  runtime.prepareAction(trusted, capability, modelProposal);

// authorize samples runtime.clock() once for this decision. Only after
// identity, tenant, run, audience, fresh expiry, scope, tool, object,
// destination, provenance/DLP, sandbox, and approval checks succeed does it
// call authorizationState.consumeAtomically({ capability, approval }).
const decision = runtime.authorize({
  trusted,
  capability,
  action,
  approval
});

TrustedContext deliberately carries no authority time. authorize samples the application-owned clock once for every decision; missing/invalid clock data returns CLOCK_UNAVAILABLE. Before invoking the resolver, prepareAction refuses foreign/unverified brands, stale capability, binding mismatch, wrong proposal tenant, and ungranted tool, scope, object, or destination; missing, malformed, or throwing resolution also fails preparation. The resolver input binds the exact payload/tool/destination to trusted tenant/run; its result binds source lineage and final normalized/encoded arguments into the prepared-action digest. All checks happen before the single atomic capability/approval transition, so a denial cannot burn either state.

Safe offline lab steps

  1. Create starter/src/security-policy.ts with explicit types for trusted runtime context, verified capability, model proposal, prepared action, bound approval, and decision.
  2. Define a strict tool registry for the three safe adapters: synthetic ticket read, reply-draft save, and approval-preview creation. Unknown tools and unknown fields deny.
  3. Resolve object ownership from an in-memory tenant map. Do not trust a tenant field in the proposal and do not allow selectors or wildcards.
  4. Inject an application-owned clock(); sample it once per authorization for capability and approval expiry. Throwing or non-finite clock output denies with CLOCK_UNAVAILABLE before state consumption.
  5. Implement ordered, deny-by-default checks for user, agent, tenant, run, audience, fresh expiry, tool, scope, object, destination, provenance/DLP, and sandbox.
  6. Call prepareAction(trusted, capability, proposal) to bind an immutable action to the verified run. Require an approval digest for draft/preview effects; mutate each true argument after approval and prove the decision changes to ARGUMENTS_CHANGED.
  7. Resolve provenance in application code over the exact frozen canonical proposal. Bind the result into the action digest; reject caller labels, missing/unknown classification, lineage mismatch, and a forged downgrade.
  8. Scan every final outbound argument after normalization/encoding. Prove an encoded canary and restricted derived content are denied at the allowed fake external:synthetic-status sink, so a destination rule cannot mask DLP.
  9. Emit minimal audit records: run/capability/agent/user pseudonymous IDs, canonical tool, object count, decision, reason, policy version, and argument digest. Do not log content or credentials.

Acceptance tests

  • User and agent have distinct, non-empty identities; changing either causes a denial with a stable reason code.
  • Tenant, scope, object, audience, fresh expiry, run, atomic use count, tool, destination, provenance, DLP, and sandbox are each covered by positive and negative tests.
  • The default path, unknown tool, unknown field, empty scope, wildcard object, invalid time, and missing approval all fail closed.
  • Approval is bound to the run, capability, canonical prepared-action digest—including resolved provenance—and an unpredictable nonce. Every check precedes one atomic capability/approval transition; denial consumes neither, replay is rejected, and execution uses the prepared object reviewed.
  • An allowed fake external sink still rejects restricted lineage, forged/missing classification, and exact or encoded fixture canaries across final outbound arguments; no network traffic occurs.
  • Audit evidence can explain every decision without storing fixture content, raw tokens, secrets, or private reasoning.
  • Tests run offline and deterministically with a pinned application clock and provenance resolver, no dependency on a real identity provider, live data, network, or tool.
