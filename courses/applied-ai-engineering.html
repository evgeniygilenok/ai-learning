Main course · last reviewed 2026-07-20

Applied AI Engineering: from real model call to public production proof.

A self-paced course for an experienced TypeScript/product engineer. Build one regulated-domain, model-driven support system in stages, test failure as deliberately as success, and finish with inspectable public job-ready evidence.

Prerequisites

  • Senior-level TypeScript and web/backend fundamentals.
  • Node.js 22+ and a local terminal.
  • Comfort with HTTP, schemas, async work, tests, and basic system design.
  • No ML research or advanced mathematics required.

Completion standard

Pass every core stage gate, maintain the completion record, and deliver an end-to-end walkthrough from user need through feedback-driven improvement. Page views and easy drills do not count as mastery.

How the path works

Core and sequential

Stages 1-6 and 8 form the job-ready spine. Complete their gates in order.

Real after Stage 1

The fake provider remains for deterministic tests. Every Stage 2+ core gate also requires a redacted real-model run and trace.

Supporting and parallel

Use quantitative/provider tracks where the project needs them; run orientation and career proof alongside the build.

Advanced specialization

Agent runtime, real-agent stack, and workflow engineering deepen agent-heavy roles after their prerequisite core gates.

Experienced-engineer agentic track · 10-12 weeks at 8-10 hours/week

Use this overlay if you already have senior product/backend fundamentals. It preserves every gate and lesson URL while bringing real agent work forward.

  2. Weeks 2-3: controlled workflows 0010-0011, then agent runtime 0031-0035 with real model proposals and approval evidence.
  3. Weeks 4-6: real-world agent stack 0050-0053: LangGraph/Postgres, MCP, hosted OTLP evals, and context compaction.
  4. Weeks 7-8: agent evaluation 0025, 0034, and 0037; fill retrieval/security gaps needed by the flagship.
  5. Weeks 9-10: public portfolio gate 0026-0030 and deployment 0039-0040.
  6. Weeks 11-12 buffer: posting-driven gaps, interview drills, and feedback-driven improvement.

Senior diff reviews: lessons 0013, 0018, and 0020 are not generic rebuilds. Keep their gates, but document only what model uncertainty, tenant-aware retrieval/tools, provider limits, or AI observability changes from systems you already know.

Flagship project

Default: a regulated-domain support and case-triage assistant over synthetic policy documents. It grows from structured model output into cited retrieval, controlled tools, resumable workflows, release gates, hardened operations, deployment, and adoption evidence.

Start in starter/. You may substitute another domain only if you document equivalent users, authoritative sources, permissions, risky actions, failure costs, and quality criteria.

Common evidence bundle

Working behavior

A reproducible command, UI path, test, or demo. After Stage 1 this means deterministic tests and at least one redacted real-model run/trace.

Failed run

A preserved real or injected failure, diagnosis from trace/eval evidence, and the resulting change.

Quality result

An eval or structured review with representative cases, slices, and stated uncertainty.

Operational observation

Latency, tokens/cost, rate-limit, queue, SLO, security, rollout, or user-feedback evidence.

Decision record

A concise tradeoff, alternatives considered, evidence, decision, and revisit trigger.

Challenging stage reviews

  1. Product foundations: the provider streams plausible but schema-invalid output while nearing a rate limit. Preserve useful UX and fail the contract safely.
  2. Grounded retrieval: aggregate retrieval improves while policy-version questions regress. Identify the misleading score and decide whether to ship.
  3. Controlled workflows: a write succeeds but the acknowledgment times out. Resume without duplicating the side effect.
  4. Production boundaries: a faster model lowers cost but changes refusal behavior for a regulated slice. Make and defend the release call.
  5. Enterprise hardening: a reranker improves relevance but exposes an unauthorized candidate in a trace. Diagnose the boundary failure.
  6. Portfolio gate: a reviewer challenges whether your evals resemble real use. Show sampling logic, limits, and the next evidence you would collect.
  7. Deployment and adoption: users bypass citations because they slow the task. Improve adoption without weakening trust controls.

Default 14-18 week pacing

Weeks 1-2: orientation and foundations. Weeks 3-4: grounded retrieval. Week 5: controlled workflows. Weeks 6-8: production boundaries. Weeks 9-10: enterprise hardening. Weeks 11-12: portfolio gate. Weeks 13-14: deployment and feedback. Weeks 15-18 are specialization or buffer. Use the 10-12 week agentic track above when senior engineering fundamentals make the diff-review treatment appropriate.

Optional extension briefs

Multimodal documents

Add one scanned or image-rich source. Preserve provenance, authorization, extraction confidence, citations, and modality-specific eval cases.

Vision input

Add one image-triage task with consent, retention, unsupported-content behavior, and calibrated human review.

Voice/realtime

Add turn-taking, interruption, latency budgets, confirmation before action, transcript policy, and replayable evals.

Local/open model

Repeat one fixed task and compare quality, hardware, privacy, latency, operations, and model-update responsibility.

Fine-tuning experiment

Only after a stable task and baseline: split suitable data, define success first, compare against prompt/retrieval/tool alternatives, and document rollback.

Final completion gate

  • All core lesson contracts and stage gates are complete; every Stage 2+ bundle links deterministic evidence plus a real-model trace.
  • The flagship workflow is driven by real model tool proposals through application-owned policy, approval, and idempotency gates.
  • A clean checkout can run representative tests; an API-key checkout can run real triage and agent paths.
  • The learner has a LangGraph/Postgres build with a level-3+ decision record, a working least-scope MCP server, a hosted OTLP eval gate, and measured context compaction.
  • The public proof package includes repo, case-study README, hosted/auth-gated demo, 3-minute video, and one technical deep dive.
  • The role-proof matrix is derived from 15-20 dated live postings, and every row cites a source.
  • The learner can show a failed real run, diagnose it, change the system, and explain the measured result.
