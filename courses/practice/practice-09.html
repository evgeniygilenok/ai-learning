09. Delegate one bounded responsibility

15 minutes explanation · 55 minutes building · 20 minutes review

Prerequisites: practice-08.

What you will demonstrate

  • Define a reviewer's input, output, visibility, and failure behavior
  • Compare a delegated path with a single-role baseline

The role contract, comparison, and retain-or-remove decision are recorded. Delegation does not change the approval boundary.

Understand the mechanism

A second role is useful only if its review changes a decision or catches an error worth the extra calls. Give it a bounded responsibility: assess whether an escalation reason follows from the supplied policy and transfer facts. Its output is advisory. It has no tools and cannot approve the proposal.

Use sequential calls for this exercise. Send only the evidence and draft required for review. Define a structured response such as supported, unsupported, or uncertain plus cited source IDs. Treat that response as another untrusted model result to inspect.

Worked example

The drafter says 'three business days pending exceeds the two-day policy window.' The reviewer sees the policy chunk and lookup result and returns supported. Change the draft to 'the transfer settled yesterday' while preserving the evidence. A useful reviewer returns unsupported and names the missing settlement fact. Neither answer creates an escalation effect.

// Learner-owned reviewer request, no tools supplied.
// Input: policy source IDs, lookup facts, exact pending reason.
// Output: { verdict: 'supported' | 'unsupported' | 'uncertain', sources: string[], reason: string }
// Final approval still belongs to the local operator.

Run shell examples at the repository root. Commented sketches describe learner code to write; they are not additional installed commands.

Guided build · 30 minutes

  1. Freeze three draft-and-evidence pairs, including an unsupported assertion.
  2. Run the single-role baseline and then one tool-free reviewer call per pair. Share a total call and token budget.
  3. Record errors found, extra usage, latency, and manual review effort. Decide whether to keep the role.

Your task · 15 minutes

Try a fourth pair where the policy is missing. Define how uncertainty returns to the operator and compare the reviewer with a direct deterministic evidence check.

Failure investigation · 10 minutes

The reviewer confidently approves an unsupported draft. Preserve it as a model-review failure and show that its verdict did not grant runtime permission.

Before running, predict the state, evidence, and effect count. Then compare your prediction with the record and name the responsible layer.

Exit explanation · 20 minutes

What information did the reviewer see, what did it miss, and what measured benefit justified its cost?

Explain the result in your own words and link the supporting command, code change, or redacted record. A missing prerequisite uses the next session's time.
